## Context

ConfigModule является фундаментальным модулем в архитектуре приложения, отвечающим за загрузку и валидацию всех конфигурационных параметров. Согласно архитектурным паттернам проекта, ConfigModule должен быть глобальным и инициализироваться первым, так как все остальные модули зависят от конфигурации.

### Constraints

- Приложение не должно запускаться с невалидной конфигурацией (fail-fast pattern)
- Путь к конфигурационному файлу определяется через переменную окружения `CONFIG`, по умолчанию `config/local.yml`
- Конфигурация может быть расширена/переопределена через переменные окружения (имитация flat nesting)
- Использовать Zod для валидации (уже включён в зависимости)
- TypeScript типы должны выводиться из Zod схемы для согласованности
- Конфигурация читается только один раз при старте приложения (no re-read)

### Stakeholders

- Все другие модули приложения зависят от ConfigModule
- DevOps и разработчики должны получать понятные сообщения об ошибках конфигурации

## Goals / Non-Goals

### Goals

- ✅ Централизованная загрузка и валидация конфигурации из YAML файла
- ✅ Поддержка переменной окружения `CONFIG` для указания пути к файлу конфигурации
- ✅ Поддержка расширения конфигурации через переменные окружения (формат: `SECTION_KEY_VALUE`)
- ✅ Fail-fast на неверной или отсутствующей конфигурации
- ✅ Type-safe доступ к конфигурации через TypeScript
- ✅ Глобальная доступность ConfigService через DI контейнер
- ✅ Единый метод для доступа ко всей конфигурации без методов-обёрток
- ✅ Покрытие тестами основных сценариев

### Non-Goals

- ❌ Hot-reload конфигурации в runtime (требует перезапуска приложения)
- ❌ Мульти-окружение конфигураций (только local.yml на этом этапе)
- ❌ Динамическая валидация при изменениях (валидация только при старте)
- ❌ Шифрование чувствительных данных в конфиге (plaintext для простоты)

## Decisions

### Decision 1: Use Zod for Schema Definition

**Rationale**: Zod уже включён в зависимости, обеспечивает runtime валидацию и генерацию TypeScript типов из одной схемы (single source of truth). Это предотвращает рассинхронизацию между схемой валидации и типами TypeScript.

**Alternatives considered**:

- class-validator + class-transformer: Требует больше кода для определения схемы, хуже интеграция с TypeScript infer
- Joi: Отличная валидация, но poorer TypeScript integration и генерация типов
- io-ts: Сложный API, более крутая кривая обучения

### Decision 2: Fail-Fast Error Handling

**Rationale**: Приложение не должно запускаться с невалидной конфигурацией. Аварийное завершение с детальным сообщением об ошибке позволяет быстро обнаружить и исправить проблемы конфигурации.

**Implementation**: Конструктор ConfigService выбрасывает исключение при:

- Отсутствии файла конфигурации (файловая ошибка)
- Неверном формате YAML (парсинг ошибка)
- Ошибка валидации Zod (детальный список проблем)

### Decision 3: js-yaml for YAML Parsing

**Rationale**: Зрелая библиотека с хорошей поддержкой TypeScript и интеграцией с Node.js fs module. Позволяет парсить YAML и обрабатывать ошибки парсинга.

**Alternatives considered**:

- yaml (Eemeli YAML): Более современная, но менее популярная
- Пользовательская реализация: Избыточная сложность

### Decision 4: Global Module Scope

**Rationale**: ConfigModule используется всеми другими модулями приложения. Глобальный модуль устраняет необходимость импортировать его в каждый модуль отдельно, упрощая зависимость.

**Implementation**: Использование `@Global()` decorator и импорт только в AppModule.

### Decision 5: Read Synchronous File Loading

**Rationale**: Конфигурация должна быть доступна до запуска остальных модулей. Синхронное чтение гарантирует, что конфигурация загружена полностью перед DI инициализацией.

**Implementation**: `fs.readFileSync` в конструкторе ConfigService.

### Decision 6: Type Inference from Zod Schema

**Rationale**: TypeScript типы выводятся из Zod схемы, обеспечивая single source of truth. Это предотвращает расхождение между runtime валидацией и compile-time типами.

**Implementation**: `export type Config = z.infer<typeof configSchema>;`

### Decision 7: Environment Variable Override Pattern

**Rationale**: Переменные окружения позволяют переопределять значения из YAML файла и добавлять новые параметры без модификации файла. Это важно для CI/CD и production окружений.

**Implementation**:

- Чтение переменной окружения `CONFIG` для определения пути к файлу (default: `config/local.yml`)
- Преобразование переменных окружения в nested structure (например, `OPC_PORT` → `opc.port`)
- Environment variables имеют приоритет над YAML значениями
- Использование `process.env` для чтения переменных окружения

**Naming convention**: `SECTION_SUBSECTION_KEY` (например, `OPC_PORT`, `MQTT_BROKER`, `DATABASE_HOST`)

**Alternatives considered**:

- Плагин для NestJS Config (@nestjs/config): Зависимость от дополнительной библиотеки, сложнее для простых случаев
- Отдельный env файл: Дублирование логики, лишний файл

### Decision 8: Single Configuration Access Method

**Rationale**: Один метод для возврата всей конфигурации упрощает API и предотвращает создание множества методов-обёрток. Пользователь получает типизированный объект и обращается к его свойствам напрямую.

**Implementation**: Единственный публичный метод `getConfig(): Config` который возвращает весь объект конфигурации с полной типизацией.

**Alternatives considered**:

- Методы для каждого параметра (`getOpcPort()`, `getMqttBroker()`, etc.): Избыточный код, хуже масштабируемость при добавлении новых параметров
- Generic `get<T>(key)`: Меньшая типобезопасность, ошибки только в runtime

## Risks / Trade-offs

### Risk 1: Environment Variable Naming Conflicts

**Risk**: Переменные окружения могут конфликтовать с системными переменными или другими библиотеками.

**Mitigation**: Использовать префикс или специфичные имена (например, `OPC_PORT`, `MQTT_BROKER`). В документации указать все поддерживаемые переменные окружения.

### Risk 2: Synchronous File Reading Blocks Event Loop

**Risk**: `fs.readFileSync` блокирует event loop, что может вызвать задержки при большом размере конфигурационного файла.

**Mitigation**: Конфигурационный файл небольшой (< 10KB). Блокировка происходит только один раз при старте приложения, что приемлемо.

### Risk 3: No Runtime Configuration Updates

**Risk**: Изменения в конфигурационном файле не применяются без перезапуска приложения.

**Mitigation**: Это сознательное ограничение (Non-Goal). Горячая перезагрузка конфигурации добавляет сложность и не требуется в рамках текущего scope.

## Migration Plan

### Phase 1: Implementation (Current Proposal)

1. Создать ConfigModule и ConfigService
2. Определить Zod схему для всех секций конфигурации
3. Интегрировать в AppModule как первый импорт
4. Написать unit тесты

### Phase 2: Module Adoption (Future)

1. Обновить существующие модули для использования ConfigService вместо чтения напрямую из файлов
2. Удалить прямое чтение конфигурационных файлов из других модулей
3. Обновить все mock в тестах для использования ConfigService

### Rollback

В случае проблем ConfigModule можно временно удалить из AppModule, что восстановит поведение без валидации (но без централизованной конфигурации).

## Open Questions

1. **Q**: Должен ли ConfigService кешировать конфигурацию или перечитывать файл при каждом обращении?
   - **A**: Кеширование при загрузке. Конфигурация должна быть неизменяемой в runtime.

2. **Q**: Нужно ли добавить поддержку секретных менеджеров (например, AWS Secrets Manager, HashiCorp Vault)?
   - **A**: Нет, это вне scope текущего proposal. Может быть добавлено в будущем как отдельный feature.

3. **Q**: Как обрабатывать конфликты между YAML и environment variables?
   - **A**: Environment variables имеют приоритет над YAML значениями (override pattern).
